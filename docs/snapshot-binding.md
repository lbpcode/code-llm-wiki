# Snapshot Binding and Recovery

Use this contract before independent Review, human approval, publication, or resuming any of those operations. It defines durable files and Git checks, not a runtime. The record shape is references/snapshot-binding-template.md.

## 1. Identity, storage, and references

- Allocate a unique `binding_id` for each frozen candidate and bind it to one `change_id`. Use `schema_version: 1`. Never reuse an ID for changed bytes or overwrite an existing binding.
- Store the immutable bundle outside the candidate tree in an authorized, durable records directory/repository. A default layout is a sibling `<wiki-name>-records/` containing `registry.yaml` and `bindings/<binding-id>/binding.yaml` plus `candidate.patch`. Temporary directories are suitable for synthetic tests, not durable production handoff.
- `registry.yaml` identifies `registry_id` and the Wiki repository. The destination AGENTS.md or authorized handoff records a portable registry locator (workspace-relative directory or credential-free shared repository/artifact URL and revision), plus any local mount mapping. An absolute path on the generator's computer alone is insufficient.
- Every `snapshot_binding_ref` has the same shape: `{registry_id, binding_id, record_path}`. The path is registry-relative, must equal `bindings/<binding-id>/binding.yaml`, and must not escape the registry. Resolve relative payload paths from the binding file's directory, never from the current working directory.
- The candidate may contain this stable reference before the bundle is complete. It must not contain its own binding digest. Completed gate reports, Human Decision, and publication records repeat the reference and `snapshot_binding_sha256`, the SHA-256 of the exact binding.yaml bytes. A binding does not store its own digest.
- Immutable payloads are written first, then binding.yaml last through atomic create/rename. A partial directory is not a completed binding. Live execution state and reports live separately under `changes/<change-id>/`, not inside the immutable bundle.

## 2. Freezing a complete candidate

Record the exact base Wiki commit and candidate Git tree OID. A commit-backed candidate also records its commit; a patch-backed candidate leaves that field null. Both include a complete binary patch and its SHA-256 for portable inspection, generated by docs/human-review.md section 4. Include additions, changes, deletions, modes, and all administrative changes; never use a worktree diff that loses untracked files.

For each changed path record its before/after Git mode and SHA-256 of the Git blob bytes, using null for an absent side. Symlinks hash the link-target blob, not the file they point to. Preserve binary content and executable bits. If the host cannot faithfully inspect a file type, report it and block approval instead of omitting the path.

The binding also records Source Manifest path/version/digest, source repository IDs/full commits, changed page/Claim scope, and the immutable publication-plan path/digest when publication is in scope. The plan uses references/publication-plan-template.md; its template describes permitted transformations, not an authorization. A candidate without a plan may be reviewed for knowledge, but publication requires a plan bound to the review/approval package; adding/changing that plan creates a new binding and requires renewed applicable review/approval.

`source_manifest.version` copies the manifest's `schema_version`; it is not a content revision counter. The exact manifest bytes are identified by the digest, alongside the pinned source revisions.

## 3. Verification in every fresh session and at each gate

1. Resolve the registry and exact binding reference from the task/handoff or Change Set. Check registry identity, schema version, binding ID, and Change ID. Obtain the expected binding digest from the completed upstream report/decision or authorized handoff; do not silently replace it with a newly calculated value. At first Review, the orchestrator establishes it when freezing and supplies it to the reviewer.
2. Hash binding.yaml and every referenced immutable payload before use. Check payload paths stay within the bundle. A digest stored next to modified payloads is not permission to update an upstream report's expected digest.
3. Resolve the base commit from the identified Wiki repository. Reconstruct the candidate in an isolated disposable worktree/index, apply the exact patch, and verify its complete tree OID. For commit-backed bindings, also verify the candidate commit resolves to that same tree and the declared base-to-candidate patch. Do not apply recovery patches over the user's working tree.
4. Compare the actual changed-path set, before/after blob bytes and modes with the binding. Check the reconstructed manifest digest/version, original source commits, page/Claim scope, and plan digest. A patch that applies cleanly is insufficient if the reconstructed tree or scope differs.
5. Verify Lint/Review/Human Decision records all identify this same reference and digest plus matching candidate/source values. Record a verification result with checked timestamp, verifier/session identity, resolved locations, and limitations in the execution workspace. Reuse findings only for this verified snapshot; never infer completed gates from a filename or a new session.

Missing registry/payload/commit, unsupported schema, digest mismatch, conflicting IDs, out-of-bundle paths, or scope/tree mismatch blocks continuation. Do not guess a replacement path/branch or update hashes to make altered content pass. Report `run_outcome: BLOCKED`; invalidate a returned mismatched Review as `INVALID` with null decision, and mark an existing approval `approval_stale` when its binding is violated. Keep the last valid workflow state otherwise. Recovery requires the exact original bundle or a new binding with the applicable gates rerun.

## 4. Handoff and archival

A handoff includes the binding reference/digest, portable registry locator, Wiki/source repository locators and revisions, execution/report references, requested stop boundary, and next action. Another Agent repeats section 3 using those files; chat history is unnecessary.

Archive the entire bundle byte-for-byte, retaining its relative layout and ID, plus bound reports/decisions under the authorized records archive. A Wiki-local mirror may live at `wiki/_meta/record-archives/<registry-id>/`, retaining `bindings/<binding-id>/...`. Update only the registry's authorized locator/mirror mapping, never immutable bundle bytes or previously recorded reference/digest. Verify the archived copy before relying on it, retain the original through publication/recovery, and report unavailable archives. Conflicting copies for one binding ID block use; do not choose the newest file.
